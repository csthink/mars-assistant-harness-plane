本设计是融合线之后产品线仓的交付方法权威（L0 治理协议）。
它规定一个受治理产品线仓从建立到持续交付的全过程：四段旅程、任务滚动环与其 Git 物理层、冻结件修正语义、评审插件矩阵、机械提醒器契约。
交付仓 `csthink-harness-plane` 是本方法的第一个实例（自我治理）；下游产品线仓自安装 HarnessPlane 起适用。
旧方法 `HarnessPlane_MVP_Rolling_Delivery_Method_Design_v1.md`（FINAL FREEZE，定位基准 `763c104`）自本设计生效起降为语义参照，不再是权威。

本方法要同时防住两类相反的失败：

- 以治理为名把合理修改挡在路上。实测案例：改一行任务名单走了 5 轮跨模型提供方评审。
- 以灵活为名随意修改导致不一致。实测案例：冻结件里的归属陈述随上游变旧后无人发现。

产品定位句（Owner 纲领，逐字转录）：HarnessPlane 用于增强产品的治理能力，但绝对不能让治理能力成为限制产品开发的障碍。

## 3. 设计原则（纲领转录，来源 = Owner 2026-08-23 对齐裁定，台账 OD-138 追记一至三）

1. 机制即产品：gov 任务与 feature 任务同为产品交付，任何文法不得把任务前缀、文件名等身份词写死为封闭枚举。
2. 可插拔总原则：凡可做成可插拔的机制尽量做成可插拔；插件供裁量，不供拦路。
3. 不可拔底线恰好两样：记入记录（Changelog、修订号、证据）与 Human 终裁。前者保证改动显式可追溯，后者是权威本体。
4. Human 终裁权在判断域绝对：任何判断性插件的结论（跨模型提供方评审结论、机械提醒红绿）都不绑定 Human。
   带保留接受时结论不涂改、显式记入记录，形态对齐 `spec-fused.md@r2 FR-26` 的 Accept With Reservation。
   确定性域的边界见原则 9。
5. 轻量可追溯：修正的最小仪式 = 直接修改 + Changelog + 机械事实在案 + Human 拍板，不设固定多步重流程。
6. 机制防的是随意乱改导致不一致，不得成为合理修改的拦路石（Owner 原话）。
7. 一图一权威边界：每张图有唯一权威面，不复述他图内部；`MVP_Workflow_v5.png` 拓扑保持不变。
8. 不被旧轮子限制：本方法按融合世界的需求重建；旧仓机制与旧方法仅作语义参照，不因既有实现反推需求。
9. Verify 中适用的预定义确定性检查不通过时不可向前绕过（proposal §4、FR-23、FR-42）。Human 可修复破坏面、修正检查本身后重跑，或 Close Task；不得将 FAIL 宣布为 PASS。layout / manifest 不属于默认必执行集合，人工调用只报告实际检查结果，不改变提交或合并权限。
10. **设计的改动面尽量局部化**（**纪律，非判定项**；Owner 2026-08-25 裁定新增并取纪律形态）。动机：既有大型单体工具表明，把持续增长的规则、用例与配置集中在手写代码分支中，会扩大变更半径与维护成本。实践建议：会随需求增长的部分（判定规则、测试用例、配置、清单）尽量以数据声明承载而非代码分支；每处相同的样板尽量只实现一次；依赖方向尽量单向。**本条不设统一机械判定标准，不单独构成合规判否项**——设计是否模块化、改动是否牵动过大属工程判断；评审可根据具体耦合与维护风险提出 blocking 或 non-blocking finding，Human 终裁不受其约束。

## 4. 权威层级

```text
proposal
  ↓ 定义产品意图与旅程（Stage 0 产物，spec 的前置输入，FR-11）
spec
  ↓ 定义产品目标、范围、需求与成功条件
milestones
  ↓ 安排交付阶段、任务身份、依赖与验收；任务在名单中登记（FR-13）
公共 Decision
  ↓ 补充跨任务复用的技术规则，不得覆盖上游
Task（任务定义）
  ↓ 定义当前任务契约
Implementation
  ↓ 实现冻结后的任务契约
```

- 下层只能安排上层范围内的内容；下层与上层冲突时停止上报，不得自行调和。
- Task 起草必须反查 spec、名单唯一条目与全部适用的冻结 Decision。
- 实现只实现 Human 定稿后的任务契约，不从周边代码或偏好扩大范围。

sdd/architecture.md 与变更 design 是非冻结工程材料，不插入上方权威链、不作为额外 Task Source，也不承接 spec 留给下游的规范性决定。architecture 按需说明现存组件/接口与 spec/Decision 指针；状态机/编排施工前独立起草，check/init/fix 不以其存在为前置。design 按 §6.2 说明已授权契约范围内的方案，发现上游缺口须按决定归属回相应正本处理。

## 5. 四段旅程

### Stage 0 前置 · 产品线仓建立与安装

- 人创建或选择 Git 仓库：可以是新建仓，也可以是已有源码、历史和工具配置的存量仓；机制只引导，不代建、不要求清空或重排已有项目。
- 安装 HarnessPlane：机制载荷以本仓 `mechanisms/`、`.agents/` 与 apps/ 为源，下游获得安装形态与适用骨架，不复制本仓实例或治理历史。安装与升级仍保护该产品线的治理资产。
- 存量接入按 FR-57/58/59：check 只读检查现有事实，不创建仓内副产物；init 先供人核对接入候选，保留已有指令及构建/测试/CI 配置，同名冲突和未知归属不覆盖；fix 只处置本产品拥有的安装与接入产物，经该次授权后修改并复核，业务源码改动仍走正式任务。
- 空规格基线不阻止上述检查与接入；安装成功只证明实际安装结果，不证明 proposal/spec/milestones 已定稿或冻结，也不等于 FR-18 来源核验通过。需要正式 feature 时继续 Stage 0/1/2，再按 §6.1 核验四件来源，不能直接由任意 issue 或安装结果进入 Stage 3。

### Stage 0 · proposal 引导创作

- 内置引导 skill 按模板骨架引导对话，区分新建产品与存量项目的实际情境，产出 proposal 候选。存量仓可在授权后以可查的已有代码、文档与用户确认事实起草候选；标明事实来源与仍待确认的产品取舍，不伪造过去的评审、定稿或授权，也不把扫描结果自动提升为产品权威。
- 候选走 §8 该对象类的插件配置，Human 定稿 FINALIZED。
- 定稿 proposal 是 Stage 1 的前置输入（FR-11）。
- 定稿后可另获授权建立非权威 prototype，允许自包含单文件 HTML；其落点与首实例命名由布局规则及该次授权确定，不建空壳、不建 Freeze Record、不作任务上游定位基准。

### Stage 1 · spec 生产

- 以定稿 proposal 为定位基准起草 spec 候选。
- 顺序固定：起草 → 评审插件（按矩阵）→ Human 处置与整改 → Human Freeze（FR-12）。
- 未冻结的 spec 不能成为 milestones 的权威输入。
- 已建立 prototype 时，把 spec 候选与其对照，记录符合处、差异和仍需 Human 判断的内容；产品规则冲突须改相应候选或走 amendment，prototype 本身不能覆盖 spec。

### Stage 2 · milestones 生产

- 以冻结 spec 为定位基准起草 milestones 候选，只安排 spec 范围内的交付。
- 顺序同 Stage 1（FR-13）；任务在名单中登记并获得唯一任务 ID。
- 未冻结的名单不得授权进入任何 Milestone 或任务。

## 6. Stage 3 · 任务滚动开发

### 6.1 外环（Milestone 层安排）

- Milestone 编号是身份不是顺序：不存在「必须先完成 M-01 才能推进 M-02」的规则。
- 任务选定的机械约束恰两条——依赖满足与并发容量可用（FR-32：未终态任务数低于并发上限）：一个任务的全部依赖已达成且并发容量可用，它即可被选定，跨 Milestone 选定亦然；多个 Milestone 的任务可交错推进。
- 在依赖满足的候选任务中选哪一个，属 Human 决定，不由任务图或编号机械推导。
- UI Gate：低保真允许自包含单文件 HTML；该格式不使其等同 proposal 的非权威 prototype，仍按本条完成视觉评审与冻结。本 Milestone 无 UI 新增或变更时，显式记录 not applicable，不造形式化 UI 任务；有 UI 变更时，先完成低保真任务、再完成高保真任务，各经独立视觉评审并由 Human 冻结，然后才可施工依赖它们的前端任务。
- 选定任务，有界并发（FR-32 任务有界并发推进：未终态任务数任一时刻不超过并发上限；并行开工形态与上限承载照 D-09@r1）。
- 反查上游：正式 feature 最小来源四件定位基准（FR-18，缺一不可）= 同仓 Stage 0 定稿 proposal + Stage 1 冻结 spec + Stage 2 冻结 milestones + 唯一命中的任务条目；另加全部适用的冻结 Decision。新建与存量产品线适用同一规则；来源缺失报 UNRESOLVED、暂不可查报 INDETERMINATE，不能把 check/init 成功视为 RESOLVED。
- 任务类型含 feature 与 hotfix（FR-15）：feature 在名单中登记；hotfix 不在名单中登记，其来源经产品内登记承载，登记首次成功持久化生成不可变登记标识（FR-19）。hotfix 同受有界并发约束，上限占满时处置路径 = Human 对某一未终态任务行使既有 Gate 权力（Close 或推进至终态）后再接纳（FR-32）。
- 公共 Decision 暂停机制：施工或验证中暴露跨任务公共技术问题时，暂停相关施工，按 Decision 机制（gov-t25 承载）建立并冻结该 Decision，任务引用后恢复。
- 任务进入内环（§6.2）；未终态任务数低于并发上限时方可选择下一任务。
- Milestone 完成判定独立于编号顺序：required 任务全部 done、依赖 Decision 已冻结并被正确引用、验收条件满足、未处理的 failure 与保留意见显式记录、含 UI 变更时已做 UI 偏离评审时，由 Human 判完成。
- Milestone 完成不自动授权任何后续；最终以端到端验收收官。

### 6.2 内环（任务生命周期）

内环拓扑 = `MVP_Workflow_v5.drawio`，本设计引用、不复述、零改动：
Define Task → Review Definition（开关）→ Human Gate 授权冻结 → Implement → Verify → Validate Change（开关）→ Human Gate → Publish，含三处 bounded autonomous budget loop 与升级门。

- 拓扑正本 = drawio 可编辑源；PNG 为便利渲染件、不承载权威（承 production-pipeline 图先例：评审对象仅 drawio 源、此类图不再导出 PNG）。权威指针的登记更新（registry 分类与档案库 `AGENTS.md` 指针行）随本设计定稿生效批次一并执行。
- `MVP_Workflow_v5.drawio` 随本设计定稿同步整体迁入交付仓 `mechanisms/delivery-method/`（单元素材，布局 §5.1 文法允许）；创始档案库原件保留，交付仓副本与其逐字节相等。
- 自我治理建立期由人工按同一拓扑执行（对象式治理形态）；产品机械化后由 harness CLI 执行（M-04 起）。
- 内环各评审开关的语义并入 §8：Task 文档与实现的跨模型提供方评审默认关、Human 按事实裁量加开（Amendment 8）；Human 定稿与 done 判定永远必需，且不被评审结论绑定。

**变更 design（Implement 前的工程输入，不新增 Workflow 节点）**：

- 满足任一条件时，在相关实现前准备 design：跨模块/机制、改变接口或数据模型、涉及授权/安全/证据，或需要事先选定技术方案。评审插件是否启用不影响此义务；日常局部修改且无上述条件时可省略，理由记在该任务原有进度/过程记录，不另起审查。

- 状态机/编排施工还需本方法 §4 所述架构说明；普通 apps 代码按现有 Task/Verify/Human 权限交付，不要求每个组件另经机制出生链。

### 6.3 任意时点终止总闸

- Human 对任一未终态任务在任意时点可行使 Close Task，不限于图中三处 escalation 门的 Close 出口（FR-27）。
- 该权力是任务生命周期层的权力动作，不是新的 Node / Edge / Gate，不改变 v5 拓扑（FR-27 定性原样沿用）。
- 约束原样沿用 FR-27：方向单向，只能终止不能借此推进；in-flight 会话停止派发并如实记录；终态记录完整，终止理由类别机械区分。

### 6.4 任务分支物理层（branch-per-task）

- 任务接纳是逻辑原子操作：Task、独立任务分支与官方 Workflow Instance 三者持久建立并相互绑定后才算接纳成功（FR-15）；Task Branch 恒 checkout 于独立 worktree，由 CLI 在原子接纳时创建并绑定，失败不留下对外可见的半成品 Task；候选变更与正式完成声明承载于该分支；完整评审证据按布局 §7.5 归档，以正式记录中的引用关联（FR-22，实现由 feature-t0 承载，不能将本设计要求视为当前 CLI 已实现）。
- Publish = 推送任务分支 + 创建指向主干的 GitLab Merge Request / GitHub Pull Request（FR-29）；两者成功即 Task Published，为任务终态之一（FR-32：Published 或 Closed 为终态；未终态任务数低于并发上限时方可选定下一任务）。
- GitLab 部署期间，既有 main 服务端保护和 Fast-forward 保持。GitHub 使用 merge commit 保留原 C/H；不支持以 squash/rebase 重映射证据。主干保护按服务端实际能力核查，不从 admin 权限推导。经 Owner 明确批准的私有免费 GitHub 实例，日常 main 直推由协作规则和执行器拒绝、改动经 PR；不声明服务端阻止其他有写权限客户端直推。该例外不自动用于其他仓。
- MR/PR 合并进主干是 Published 之后的主线接纳动作，合并决定仍由 Human 作出；在核差完成后，Human 可按交接协议 §5/§6.7 的当批“交付”授权委托 Agent 使用 cst-ship 组织已有工具执行。较窄发布指令不授予 merge/delete。私有免费实例保留 PR-only 协作/执行器约束，不宣称服务端不可绕过；人工治理期 done 的收官权威保持。
- **人工期收官次序**：终态里程碑任务先由 Owner 判 done，裁定件入库仍是人工期 Published 等价时点（D-09 第3条）；其后 Owner 核差成果并下达“交付”，Agent 按 cst-ship 指引复用现有工具完成适用交付动作，保留无法安全清理的工作区并报告。仅“发起 MR/PR”时止于发布，合并及整理另依其授权。未终态任务可按合法阶段范围交付，不要求整体任务先关闭。中途 $handoff 只保存；交付完成不重开任务、不自动接纳后续任务；本条不增加 v5 节点或 Task 终态。
- 分支命名自由，是习惯约定不是规则；治理成果与冻结证据的定位基准一律用提交 SHA，不从分支命名形状推导授权、任务身份或完成。交接工具可按获授权 context 中的分支字符串查询 Git 现场与写入归属；已合入 main 的成果不依赖旧分支继续存在（handoff-protocol 设计 §3 至 §5）。
- 计划层修正（§7）同样通过任务分支和 MR/PR 交付，核差与终裁按其正本执行；唯一初始化例外为布局 §7.6 已点名批准的既有历史首次导入，不授权日常 main 直写。
- 并发边界：分支与 worktree 是承载形态，不是并行授权；并行开工按 D-09@r1 三绑定形态走，任一时刻未终态任务数不超过 FR-32 并发上限。

完整交付的中性指令为“交付”或明确执行 $cst-ship；仅发布在 GitLab 为“发起 MR”，在 GitHub 为“发起 PR”。规则由交接协议 §6.7 承载，操作步骤住 cst-ship；HANDOFF/README.md 只记入口和实际验证范围；首次历史导入按布局 §7.6 与交接协议 §6.6 保留为独立历史程序，不是日常交付前置。

### 6.5 MR 上两类检查的分工

- Verify 中适用的预定义确定性检查：FAIL 不可被带保留接受绕过或改成 PASS。Human 可修复、按 §7 修正检查本身后重跑，或 Close Task。layout / manifest 是人工可选工具，其违规结果照实保留，不参与 MR 自动阻断；Task Definition 已要求的产品检查不因本条免除。
- 判断性插件（机械提醒器、跨模型提供方评审）：只供裁量，不接入任何阻断集；其可拔性由 proposal §4 成员固定的可禁用插件名单承载（跨模型提供方评审通道增强件在该名单内）。
- 历史服务端边界：OD-113 曾验证「门没有机会跑」与「门跑完丢结论」的差别；该历史不证明当前平台状态。本仓平台治理绑定已实际退役；GitLab 期间原配置/保护保持，GitHub 私有免费实例按本节及 §6.4 的显式边界执行；现行事实与历史证据指针 = `records/GITLAB_CI_ENFORCEMENT.md`。

### 6.8 Assistant 联合实施与手动接入

联合计划只有 Assistant 正本；hp 通过布局 §6.6 的完整固定输入副本读取。文档先行、产品任务选择、冻结、实际实施、真实模型调用与发布分别按既有授权；候选副本不等于 J-01 接收。两仓分别由自身写者实施，Assistant 主 agent 核对实际候选/提交、版本、验证和残余，每个跨仓依赖绑定 J-01 至 J-07 的交付与接收记录，不以口头完成或另一仓的测试代替。

联合切片只做已确认最小路径，独立 hp web 未来范围由相应 proposal/spec/milestones amendment 一并调整，旧图稿和历史证据不改写。原型按交互需求和授权选择，不强制每个变更重做；Assistant客户端遵循其自身已签署规格和验收原型，hp不新增第二套UI冻结链。

J-07 手动接入使用已经存在的 csthink/mars-homepage 站点基线。每件机制/模板来源绑定一个固定 hp 提交，实例文件新建于下游自身治理链，不复制 hp ruling、冻结记录、开放项或归档配置身份。按 FR-18，最小 proposal、spec、milestones 与唯一任务名单项缺一不可，且各自需按既有定稿程序成立后才正式接纳；共同计划只提 proposal/milestones 的历史简述不得豁免 spec。定义评审可按既有 review-skip ruling 配置，不能把准备说明当作已作出裁定。手动接入干跑和检查是产品任务 feature-t19 的验收，文档准备不执行三个真实任务。

## 7. 冻结件修正语义

### 7.1 适用面

本节程序适用于：

- 规划基线件：proposal、spec、milestones。
- 治理机制设计（Layer 2）：各机制单元的设计正本与其同批冻结的连带件（数据文件等；Amendment 7 前称锁面连带件）。
  此为明文新设：旧方法 §6 只管 spec 与 milestones，Layer 2 修订此前以「比照 §6」惯例执行至少七次而无冻结权威；本条把该惯例转录为权威（OD-44 的闭合依据）。
- UI 设计冻结件：已冻结的低保真与高保真交付物（继承链上的设计源产物）。其修正同走本节流水线，形成新冻结修订；插件 B 对此类对象默认关、加开时取独立视觉评审（评审面照 §8 第二句），继承链下游按 §7.3 向下同步。
- 公共 Decision 的修正文法归 gov-t25；本方法只约定其同享「插件供裁量、Human 终裁」的结构，不定义其文法。
- 旧线已收束档案对象不适用。

### 7.2 修正流水线（路径一）

```text
变更需求发现
→ 直接准备候选修改 + 起草 Changelog 记录
→ 插件 A：机械提醒器运行，事实与红绿结论在案（可拔）
→ Human 裁量：是否推进到插件 B
→ 插件 B：跨模型提供方 delta review（可拔）
→ Human 终裁：冻结新修订生效，或带保留接受，或退回，或放弃
```

- 每一级插件后面都是 Human 裁量点；两级插件的默认开关按 §8 三句，关闭默认开的插件须显式记入记录。
- Human 终裁不被任何插件结论绑定：评审结论 FAIL 或机械红灯下，Human 仍可冻结文件或判任务 done，带保留接受显式记入记录、结论不涂改。
- 每次修正按 §7.5 申报分级，可按 §7.6 合为变更集（Amendment 6）：两者只改变本流水线的插件默认值、Changelog 详略与冻结提交的成员数，不改变步骤集合、Human 裁量点与 Human 终裁位置。

Changelog 最低承载（承接前版交付方法 §6 的规则 八项，在新的插件配置下的去留逐项裁定）：

1. Change Identity、日期、提出者与触发事实。保留。
2. 被修改的权威文件及原冻结 Revision。保留。
3. 修改前 / 修改后语义。保留。
4. 修改理由，以及为什么不能只在下游处理。保留。
5. 对未开始、进行中和已完成 Milestone / 任务的影响。保留；其机械来源即提醒器第三项事实。
6. 对 UI 继承链（低保真、高保真与真实现之间的承继关系）的影响。保留。
7. 原「Review target、Verdict、finding disposition 与 Owner decision」改写为：实际运行的插件清单及各自结论（含显式关闭了哪个默认插件）、Human 的处置与终裁（含带保留接受的保留内容）。
8. 新生效 Revision 与冻结记录行指针（`records/governance/<subject>/freeze-records.jsonl` 内该次记录行的 `revision`；Amendment 7 起，承 freeze-record 设计 r6：字节身份由记录行 `objects[]` 承载，Changelog 不重复转录）。保留。

禁止面（承接前版交付方法 §6 的规则，全部保留）：

- 先修改冻结件、事后补 Changelog。
- 用 Decision 或 Task 绕过上游件的修正程序。
- 因 Git 历史可查 diff 就省略语义化 Changelog。
- 让新 Revision 未显式记录就改变已完成任务的验收事实。

### 7.3 逐层上修链（路径二）

依赖定位基准链条（每个任务的上游定位基准记录在案）：

```text
proposal → spec → milestones
spec → UI 低保真（交付物 = html 与设计文档）→ UI 高保真 → 前端代码任务
spec → 后端代码任务
```

- UI 高保真严格依据当前低保真骨架、只做视觉表达；其上游依赖定位基准是低保真任务的交付物。
- 高保真定稿后，前端任务才能依据高保真设计并结合 spec 施工。

向上：任一执行层任务（低保真、高保真、前后端代码）发现上游缺失、冗余或错误时：

1. 上报事实（发现了什么、影响哪条上游条目）。
2. Human 从两种可选形态中裁定，本方法不设判别标准：其一，上游件就地修正，直接走 §7.2 流水线；其二，开修复任务承载该修正。proposal 同在可修范围内。
3. 上游按 §7.2 修正生效。
4. 两种形态均继承插件化语义：就地修正走 §7.2 双插件流水线（插件 A 与插件 B 均可拔）；修复任务走 §6.2 内环，其评审开关同为可拔。上修全程不存在任何强制跨模型提供方评审环节，是否运行与结论如何均由 Human 裁量（原则 2 / 4）。

向下：上游修正生效后：

1. 提醒器第三项事实生成受影响任务与证据清单，登记在案。
2. 受影响下游的更新由 Human 排期，不强制立即级联。
3. 由硬规则作最后约束：任务施工只认上游的冻结标记。上游修正生效即形成新的冻结修订；任务再施工前，其上游定位基准必须指向上游当前冻结修订，若指向已被取代的旧修订，先对齐新冻结修订再施工。

### 7.4 场景保证

以下高频场景的目标成本均为「一次直改 + 一次拍板」量级：

- 名单内任务拆分（范围过大拆成多任务）。
- 名单内增加任务。
- 名单内关闭任务（受影响证据由提醒器第三项事实列出）。
- spec 单条目更正。
- 上游语义修正生效后的下游级联对齐（proposal → spec → milestones，或 spec → Layer 2 机制设计）：与触发它的上游修正同一变更集（§7.6），零额外拍板；单独发起时按对齐级（§7.5）走。

### 7.5 修正分级（Amendment 6）

适用 §7.1 全部适用面。每次修正由提出者在 Changelog 第 1 项申报分级，取值恰二：

- **对齐级**：申报为对齐级，且同时满足三条判据——（一）语义零变化：不新增、删除或改变任何规范性条款的要求、判据、权力、状态值、默认值、闭集成员或适用面；（二）改动类型属闭集：措辞更正与错别字、指针 / 编号 / 修订号 / 路径更新、上游修正生效后按 §7.3 向下同步的转录（上游语义已裁定，本件只对齐）、已裁定术语的对齐、格式与排版；（三）Changelog 第 3 项给出逐处 before / after 表并声明「语义零变化」，表行与候选相对原冻结修订的 `git diff --unified=0` hunk 一一对应（每行注明 hunk 位置，hunk 数等于表行数；drawio 等非文本素材按属性级变更逐处计），漏对应即 Changelog 文法违规。
- **语义级**：申报为语义级者，或不满足对齐级任一判据者。满足三条判据而申报语义级属保守升档，合法且不构成误申报。

判定权：申报只是线索。Owner 核差时可把对齐级改判为语义级，改判即按语义级续走，已运行的插件 A 事实与已起草的 Changelog 沿用、不重来；语义级申报不改判为对齐级（保守申报无需纠正）。判据的机械可判面 = 第（三）条的 hunk 与表行对应关系；「语义零变化」本身属 Owner 核差的判断域（§3 原则 4），本设计不假称其可机械判定。

两级在 §7.2 流水线上的差异恰三处：

1. 插件 B 默认值：对齐级恒默认关（§8 第二句）；Human 仍可显式加开，加开与关闭均记入记录。插件 A 默认值两级相同。
2. Changelog 详略：对齐级八项编号保留，第 4 至 7 项各允许单句承载，其中第 5 项须含「验收事实零改变」声明与插件 A 事实或「不适用」；语义级按本节原承载。
3. 评审面：对齐级开启插件 B 时，评审面 = 逐处 before / after 表与「语义零变化」声明是否成立，不重审既有语义。

两级不变的部分（不可拔底线，原则 3）：Human 终裁形态（re-Freeze 指令）、Changelog 在案、每 subject 一行冻结记录（freeze-record 设计 r6）、Owner Decisions 条目。锁转换两提交仪式自 Amendment 7（r8）退役：其机械关口已随 `locks` 门停用不存在，Owner 2026-09-06 裁定 E1 据此把台账 `repo:OD-09`「不可减」三项减为两项（台账 `repo:OD-10`）。

### 7.6 变更集（Amendment 6；冻结提交条自 Amendment 7 起）

- 定义：同一触发事实引起的、跨多份 §7.1 适用面文件的修正，可合为一个变更集，以一份 Changelog 承载（第 2、3、8 项按成员分节）。成员可跨 subject 与跨对象类（规划基线件、Layer 2 机制设计、UI 冻结件、同单元素材）。

## 8. 评审矩阵（插件默认配置）

「required / optional」二值退役，代之以按对象类的插件默认配置；关闭默认开的插件 = 显式记入记录的偏离。当前 SC-6 按同批 spec r7 保留实际开关、运行/未运行、重新启用时点、Verdict/Findings/reservation 与 Human 决策；历史证据不改写，不再要求旧 `spec-fused.md@r2 SC-6` 的保证档案与传播等级。

默认配置恰三句（Amendment 8，Owner 2026-09-07 裁定 J11 甲；原逐对象行表的历史文本由 Git 历史与 r8 的冻结记录承载）：

1. **机制正本（Layer 2 机制设计）与规划基线件（proposal / spec / milestones）的初稿与语义级修正：插件 B 默认开**；插件 A 对其中的修正默认开（初稿不适用；机制正本修正适用时）。
2. **其余对象（规划基线件与机制正本的对齐级修正、Task 文档、任务实现、公共 Decision、UI 设计冻结件、Milestone 完成）：插件 B 默认关，Human 按事实裁量加开**；插件 A 对对齐级修正的默认值与同对象语义级相同，其余不适用。UI 设计冻结件加开时取独立视觉评审，评审面 = 文档与继承一致性（高保真对低保真的骨架承继、交付物与上游定位基准的一致），审美判断不在评审面内、由 Human 终裁。
3. **Human 终裁（定稿 / Freeze / re-Freeze / done 判定 / Milestone 完成判定）恒必需、不可拔。**

- 默认值只是默认：任一对象的任一插件，Human 均可对当次显式改开或改关，偏离默认显式记入记录（关闭默认开的即 SC-6 语义，开启默认关的同样记录）。
- 无论插件结论是 PASS 还是 FAIL，Human 均可定稿、Freeze 或判 done，带保留接受按 §3 原则 4 记入记录。
- 铁律照旧：插件工具执行成功、作者自检、一般性建议或同源自评都不构成跨模型提供方 Verdict。
- 跨模型提供方的定义按模型提供方、不按工具（Owner 2026-08-23 裁定）：Claude Code 与 Codex 均为合法 writer；评审构成跨模型提供方，当且仅当评审方的模型提供方不同于产出方的模型提供方。例：作者 Claude Code / Fable 5（Anthropic），评审 gpt-5.6-sol（OpenAI）或 deepseek-v4-pro（DeepSeek），跨模型提供方成立；作者 Codex / gpt-5.6-sol（OpenAI），评审 deepseek-v4-pro（DeepSeek）或 Claude Code / Fable 5（Anthropic），跨模型提供方同样成立。同提供方评审无论经何工具运行都不构成跨模型提供方 Verdict。

## 9. 机械提醒器

### 9.1 规则集合（首版恰好三项）

1. 覆盖丢失面：spec 条目全集减名单引用并集的差，即本次修改后哪些需求失去名单承载。
2. 依赖可达性：名单任务依赖字段构成的图在修改后是否出现断链或环。
3. 受影响面：受本次修改影响的在办与已完成任务清单，及挂其名下的既有评审证据。

集合增补或修订走 §7.2 程序，不临场扩。

### 9.2 工具契约

- 输出 = 事实清单 + 机械红绿结论；结论供 Human 裁量，永不阻断。
- 定性为提醒器非门：不得接入「Pipelines must succeed」或任何阻断集；此禁止为明文，防止部署时未经明确裁定就提升为门。
- 调用形态 = `python3 <路径>`，退出码的通过 / 查出违规 / 未查成三种结论：绿 / 红 / 自身失败。自身失败 fail-visible 不 fail-block：提醒器坏了不拦修正，但失败事实必须记入记录。
- 自证 = 可红可绿的最小正负例测试用例，随施工交付。
- 运行位置 = 随规划基线正本所在仓：过渡期在创始档案库，收束后在交付仓。
- 归属 = 本任务：规则集合与本契约随本设计冻结，工具本体按 §12 三层次序「设计冻结 → 另行授权施工 → 验收」交付（OD-145 已裁）。

## 15. 最低验收场景

### S1 · 名单拆分一次直改走通

发现某任务范围过大，直接在名单候选上拆分，Changelog 在案，提醒器三项事实在案，跨模型提供方评审未开，Human 拍板 re-Freeze。
全程一次直改一次拍板，痕迹完整。

### S2 · 显式关闭默认开插件

某次 Layer 2 修正，Human 显式关闭默认开的跨模型提供方评审，保留谁在何时关闭、作用于哪个对象、实际执行与未执行的评审/检查记录；流程经适用 Human Gate 走完，既有证据不改写，不计算保证等级。

### S3 · FAIL 带保留接受

跨模型提供方评审判 FAIL，Human 复核后判定 finding 不成立或可接受，带保留冻结；评审结论原文保留，保留理由在案。

### S4 · 逐层上修

高保真施工中发现视觉无法成立，调查确认是 spec 条目错误：上修 spec（轻档），受影响清单登记，低保真按排期对齐后高保真修复。
期间任何上游定位基准过时的任务不得施工。

### S5 · 任意时点终止

实现进行中，Human 按下终止：in-flight 会话停止派发并如实记录，终态完整，理由分类为 Human 主动终止，不可借终止推进任何状态。

### S6 · 适用 Verify 检查失败的三出口

适用 Verify 检查失败时，Human 可修复后重跑、按 §7 修正检查本身后重跑或终止任务，不得把 FAIL 改成 PASS。layout / manifest 人工运行时仍须报告真实结果，但不自动阻断提交或合并。

### S7 · Layer 2 修正按明文程序走

修正某机制设计不再需要「比照惯例」论证，直接引用 §7.1 适用面；程序与记入记录同 §7.2。

### S8 · 提醒器自身失败不拦路

提醒器运行报自身失败，修正流程照常推进到 Human 终裁，失败事实记入记录；修好提醒器不阻塞本次修正。

### S9 · 跨 Milestone 推进

M-01 尚有任务未完成，M-02 某任务的全部依赖已达成，Human 选定它推进：合法，零豁免记录。
反向核对：任何「按编号先后完成 Milestone」的读法在本方法内找不到依据。

### S10 · 对齐级修正

上游术语裁定生效后，某 Layer 2 机制设计内十余处用词须对齐：申报对齐级，Changelog 第 3 项逐处 before / after 表 + 语义零变化声明，插件 B 默认关未开，Owner 核差后 re-Freeze。
反向核对：其中一处顺手改了默认值，Owner 核差改判语义级，插件 B 默认开，已起草的 Changelog 沿用续走。

### S11 · 变更集

spec 一条需求语义修正引起 milestones 两行与某机制设计三处级联对齐：三件合为一个变更集，一份 Changelog 三节，插件 A 跑一次；插件 B 三成员均按 §8 第一句默认开，Human 一次裁量是否运行，运行覆盖三件、无偏离登记；Owner 一次 re-Freeze 指令点名三个新修订号，一次冻结提交覆盖三条路径，三行冻结记录同指该 Changelog。
反向核对：任一成员夹带与该需求无关的改动，即拆出另立。

## 16. 反思

### 必须现在定（本设计承载）

- 生效一刀切与适用面按对象不按仓（§10）：不定则复刻 OD-125 式过渡留白。
- 插件默认配置表（§8）：不定则「可拔」退化为无默认的临场争论。
- Changelog 八项的逐项去留（§7.2）：不定则轻档被读作「可以不记入记录」。
- 修正分级判据与变更集边界（§7.5 / §7.6）：不定则「轻档」退化为临场争论，级联对齐继续按文件数倍增评审与仪式（实测：CL-27 与 CL-28 同一语义变化走两遍全流程，CL-28 三轮插件 B 全落在格式面）。

### 同类潜在 bug 一并防止

- 提醒器被部署为阻断检查即未经明确裁定就提升为门：§9.2 明文禁止接入阻断集。
- 新插件或新提醒项临场加入：集合与矩阵的修订走 §7.2 程序，不临场扩。
- 交接悬空复发：§11 交接纪律，台账 open 行强制。
- 分级申报被用来把语义变化伪装成对齐级：§7.5 申报义务 + 逐处 before / after 表 + Owner 核差可改判且不可反向改判。
- 变更集被用来夹带无关改动：§7.6 同一触发事实边界，夹带即拆出。
